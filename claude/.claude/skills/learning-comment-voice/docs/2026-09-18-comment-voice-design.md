# Comment voice: learning Max's comment style from his own edits

## Problem

Claude's comments are verbose, narrate the change rather than the code, and
track problems hit along the way. Written style guides don't fix this — they are
themselves verbose, and phrasing is not a thing prose about phrasing can convey.

What does convey it is examples. Max already produces them: he walks a branch
commit by commit and rewrites comments by hand. Today that work is discarded.
This system keeps it, and feeds it back to the point where comments get written.

## Goals

- Capture comments Max writes, verbatim, with enough context to retrieve them later.
- Retrieve the ones relevant to a situation Claude is about to comment on.
- Work at 20 entries and at 5,000, with no re-capture in between.
- Degrade to today's behavior when anything is missing.

## Non-goals

- **Not a bug or correctness system.** Comment noise only.
- **Not a replacement for `rules.md`.** That rulebook decides *whether* a comment
  exists; this corpus decides *how it reads*. Keeping them separate is what stops
  the corpus from becoming another style guide.
- **Not a record of Claude's mistakes.** Claude's original comment text is never
  stored. The goal is Max's voice, not a contrastive model of what he dislikes.
- **No backfill of existing repos in v1.** Comments already committed are polluted
  with Claude-authored text Max accepted. A date-bounded blame mine is possible
  later but is out of scope here.

## Key decisions

### 1. Capture at the interactive-commit stop

`editing-commits-interactively` step 5.4 runs `git diff` after Max says he is done
editing a commit. That diff is, by construction, Max's hand edits. No journal of
what Claude wrote, no disk polling, no reflog watching, and no line-number
anchoring problem — the hunks are the evidence.

The cost is coverage: comments Max fixes outside that flow are not captured. This
is accepted. Precision matters more than volume, because a corpus with Claude's
text mislabelled as Max's poisons every retrieval that returns it.

### 2. Added and rewritten comments are voice; deleted comments are rules

Within the captured diff:

- A comment Max **added or rewrote** becomes a corpus entry.
- A comment Max **deleted** becomes evidence for `review-comments/references/rules.md`,
  not a corpus entry. A comment he removed says nothing about how he writes.

### 3. Vectors are built on the code, never on the comment

Index side and query side must occupy the same space. At query time there is no
comment — that is the point; Claude is deciding what to write. A vector encoding
what the comment *says* is unreachable from a query that has only code.

Two vectors are computed per entry and the winner is chosen by measurement:

- **`desc`** — a short natural-language description of the situation the code
  presents. Language-agnostic, so voice transfers from Go to Python.
- **`code`** — the code hunk itself. Symmetric by construction, nothing to leak or
  drift, but tends to cluster by repo and language rather than by situation.

Which retrieves better is an empirical question that cannot be answered before a
corpus exists. Both are cheap; storing both defers the decision at near-zero cost.

### 4. The capture-side description is generated comment-blind

At capture, Claude can see Max's comment, and therefore knows which aspect of the
code turned out to be worth remarking on. At query it must guess. Descriptions
written with that knowledge would be systematically better-aimed than the ones used
to search — retrieval that tests well and degrades in use.

**The description is generated by a subagent handed the hunk with the comment
stripped out.** It cannot leak what it never saw. Both ends then run the same
function of the same input.

### 5. Filter on mechanical facets only

- **Filtered:** `language`, `placement` (doc / block / trailing). Both derivable
  without judgment. Placement matters because register differs — a doc comment
  addresses a caller, a trailing comment is an aside.
- **Metadata, not filtered:** `kind` (`why` / `warning` / `contract` / `domain` /
  `pointer`). A judgment call, so it will be applied unevenly, and an uneven hard
  filter starves retrieval invisibly. Useful for reviewing the corpus by hand and
  as an optional flag.

Similarity does the ranking. Facets only remove entries that are categorically
wrong to show.

## Architecture

```
  editing-commits-interactively (capture step folded into 5.4)
            | Max says "done"; git diff = his hand edits
            v
  +---------------------+
  |  capture skill      |  public
  |  learning-          |  comment hunks -> records
  |  comment-voice      |  (description via comment-blind subagent)
  +----------+----------+
             | appends
             v
  +---------------------+        +------------------+
  |  corpus/*.json      |------->|  voice_index.py  |
  |  (untracked, local) |        |  -> vectors.npz  |
  +----------+----------+        +--------+---------+
             |                            |
             +-------------+--------------+
                           v
                  +------------------+
                  |  voice_query.py  |  facets + situation -> k exemplars
                  |  backend: all |  |
                  |  desc | code     |
                  +--------+---------+
                           | CLI, plain text
                           v
            +------------------------------+
            |  review-comments (+ writing)  |
            |  rules.md  : whether          |
            |  exemplars : how it reads     |
            +------------------------------+
```

Capture and query never call each other. They meet only at the corpus on disk.

## Components

### Capture skill — `claude/.claude/skills/learning-comment-voice/`

Invoked from `editing-commits-interactively` step 5.4, the point at which Max has
said he is done and the diff of his hand edits is on the table. Both skills are
public and the corpus is neither package's file, so the call is direct rather than
two descriptions hoping to match the same moment.

Procedure:

1. Take the diff of Max's hand edits for the current commit.
2. Keep hunks whose added lines contain comment text, in any language present.
3. Partition into added/rewritten (-> corpus) and deleted (-> rulebook evidence).
4. For each corpus candidate, dispatch a subagent with the post-image hunk **with
   the comment lines removed**. It returns the situation description and `kind`.
5. Write one JSON record per candidate.
6. Append one line to `corpus/_stats.jsonl` recording the run.
7. Report what was captured, so a wrong capture is visible immediately.

### Corpus — `$XDG_DATA_HOME/claude/comment-voice/corpus/`

One JSON file per record, named by content hash. Flat, append-only in practice, so
concurrent sessions cannot conflict. Default location
`~/.local/share/claude/comment-voice/corpus/`, overridable with `--corpus`.

**Untracked, and outside both packages.** It accumulates verbatim code from every
repository Max works in, so it belongs to the machine rather than to either half of
the dotfiles split. Keeping it out of git is what lets the skill itself be public:
the skill names a path, and the data at that path is nobody's business but the
machine's -- the same arrangement `mcphub/` has with the bifrost credentials file.

Correction is deleting a file, which needs no tooling. The cost of not tracking it
is that there is no history to audit later, so a misattribution has to be caught
when the capture run reports it. That is why the report in capture step 7 is not
optional.

Record schema:

| field | type | notes |
|---|---|---|
| `id` | string | content hash of `comment` + `code` |
| `comment` | string | verbatim, exactly as Max wrote it, markers included |
| `placement` | enum | `doc` / `block` / `trailing` |
| `language` | string | from file extension |
| `kind` | enum | `why` / `warning` / `contract` / `domain` / `pointer` |
| `code` | string | post-image hunk, comment stripped |
| `enclosing` | string? | function or type name when determinable |
| `description` | string | comment-blind situation description |
| `repo` | string | repository name |
| `path` | string | file path within the repo |
| `commit` | string | sha the edit landed in |
| `captured` | date | ISO date |

Vectors are **not** stored in the record. They are derived, and a derived value in
an authoritative file goes stale silently.

### Index builder — `voice_index.py`

Pure function of the corpus: reads every record, computes the `desc` and `code`
vectors, writes `index/vectors.npz` plus a manifest of which record ids it covers.
Regenerable at any time; never authoritative. A stale or missing index costs
recall, never correctness.

Embeddings come from a local sentence-transformer (`all-MiniLM-L6-v2`, ~80MB,
384-dim). No network, no API key, no vector database — brute-force cosine over a
few thousand vectors in numpy is microseconds. **The dependency is optional**: if
it is not importable, the index is skipped and query falls back to the `all`
backend.

### Query — `voice_query.py`

The only interface consumers use.

```
voice_query.py --language go --placement doc \
               --situation "retry loop whose backoff cap tracks an upstream timeout" \
               [-k 5] [--kind warning] [--backend all|desc|code]
```

Output is exemplars as plain text — the comment, with a line of code context each.

Backend selection, when `--backend` is not given:

- **`all`** while the corpus is small: return every entry matching the facets.
  Correct, and better than similarity search at this size.
- **`desc`** once the corpus exceeds the threshold (~150 entries, or total
  exemplar text over ~20k characters), assuming measurement has not chosen `code`.

Consumers never learn which backend ran. Switching backends changes no caller.

### Consumers

- **`review-comments`** gains a lookup before it rewrites a comment, so rewrites
  land in Max's register rather than a generic one.
- **Writing path** — the larger win. Claude queries *before writing a comment at
  all*, so the corpus shapes output rather than only correcting it. There is no
  harness event for "about to write a comment", so this cannot be a hook. It lands
  as a second trigger on the skill's own description, which fires when Claude is
  about to add comments to code it is writing.

## Failure behavior

Everything degrades to current behavior. Missing corpus, missing script, absent
sentence-transformers, stale index, empty result — all return nothing, and the
consuming skills run exactly as they do today. Nothing here sits in a path that
can fail closed, deliberately unlike the hooks in `settings.json`, which are
registered by absolute path and take down every tool call when absent.

The one failure that cannot be prevented at capture time is a **misattribution**:
a comment credited to Max because his commit-walk edit happened to touch a line
Claude authored. It is caught by step 7 of capture reporting every record it
wrote, comment by comment, and fixed by deleting the file.

## Public / work split

**Nothing here is work-private.** The skill, both scripts, and these documents live
in the public `claude` package. The feature is a generic Claude Code enhancement
with nothing internal in it.

What would have been work-private is the corpus, and it is not in the repository at
all -- it sits at `~/.local/share/claude/comment-voice/`, untracked. This is the
pattern the dotfiles rulebook already blesses: naming the path a value lives at is
public; the value is not.

A public clone with no corpus gets a working skill whose queries return nothing,
which is the same degraded path a brand-new corpus takes. There is no special case
to write.

The one work-private file this touches is `claudework`'s `review-comments/SKILL.md`,
which gains the lookup. That is a work-private consumer of a public tool, which is
the direction the split permits.

## Measurement

Each capture run appends to `corpus/_stats.jsonl`: date, repo, commit, number of
comments added, rewritten, and deleted.

The honest measure of whether any of this works is **comment edits per commit-walk,
trending down**. It costs nothing to record from the first run, and it is the only
evidence the system does anything at all.

## Deferred

- **Backend choice between `desc` and `code`.** Held-out test once a corpus exists:
  take an entry, ask each backend to retrieve for its code, see which ranks
  stylistically similar entries higher.
- **Blame mining** of pre-Claude commits as a seed corpus.
- **Capture outside the interactive-commit flow.**
